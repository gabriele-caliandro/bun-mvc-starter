# Add or change a database table

Tables are defined with **Drizzle ORM** (never raw DDL, never another ORM). Schema files are the source of truth; when the repo owns the database, migrations are generated from them, not hand-written.

## First: does this repo own the database?

Check for `atlas.hcl` and a `migrations/` directory (with `atlas.sum`).

- **Present** → the repo owns its schema; every `*.sql.ts` change goes through the Atlas migration workflow below.
- **Absent** → the repo only *queries* an existing database it doesn't control. Drizzle table files are then **mirrors of the external schema**: edit them to match reality (confirm column names/types against the real DB, not assumptions), and skip the migration pipeline entirely — never introduce one, and never "fix" the external schema from this repo.

## Where tables live

```
src/database/schemas/<app_schema>/
  <app_schema>.sql.ts          # the pgSchema definition (a named PostgreSQL schema, not `public`)
  enums.sql.ts                 # pg enums (if any)
  common/                      # shared column helpers / types
  tables/<domain>/
    orders.sql.ts              # one table per *.sql.ts file
    order_lines.sql.ts
  constraints/                 # cross-table constraints, if the repo has them
```

- One table per file, file named after the table, `.sql.ts` extension.
- Tables are grouped in per-domain directories and always created on the app's named `pgSchema`, never on the default schema.

## Table definition conventions

```ts
// src/database/schemas/app_schema/tables/orders/orders.sql.ts
import { app_schema } from "@/database/schemas/app_schema/app_schema.sql";
import { customers } from "@/database/schemas/app_schema/tables/customers/customers.sql";
import { boolean, integer, text, timestamp } from "drizzle-orm/pg-core";

export const orders = app_schema.table("orders", {
  id: integer().primaryKey().generatedAlwaysAsIdentity(),
  code: text().notNull().unique(),
  customer_id: integer()
    .notNull()
    .references(() => customers.id, { onDelete: "cascade" }),
  description: text(),
  status: text().notNull().default("OPEN"),
  is_obsolete: boolean().notNull().default(false),
  created_at: timestamp({ withTimezone: true }).notNull().defaultNow(),
  updated_at: timestamp({ withTimezone: true }).notNull().defaultNow(),
});
```

Rules:

- **snake_case** everywhere: table names and column names.
- **Primary key: an `integer` identity `id` by default** (`integer().primaryKey().generatedAlwaysAsIdentity()`). Human-readable business identifiers (`code`, `slug`) are a separate `.notNull().unique()` text column. Avoid sequence-backed prefixed defaults (`'ord-' || nextval(...)`) for new tables — sequences are harder to migrate and maintain; if the repo already uses them on existing tables, leave those as they are.
- Every table gets `created_at` and `updated_at` as `timestamp({ withTimezone: true }).notNull().defaultNow()`. Services must set `updated_at: new Date()` on update (there is no trigger).
- Foreign keys are explicit `.references(() => other.col, { onDelete: ... })` — always decide the `onDelete` behavior deliberately (`cascade` for owned children, default restrict for referenced masters).
- Soft-delete/retire flags follow the `is_obsolete` boolean pattern rather than deleting referenced master data.
- Enum-ish columns: prefer `text()` validated by the Zod DTO layer; use a pg enum only when the DB must enforce it.
- **Match existing column names exactly, typos included.** A misspelled column in production (e.g. `dispaly_color`) is load-bearing — renaming it is a migration with its own risks. Never "fix" an existing name opportunistically; flag it to the user instead.
- The Drizzle row type is **not** the DTO. Never export `$inferSelect` types for use outside the service layer, and never derive Zod schemas from tables (see the `dto-conventions` skill).

## Migration workflow (Atlas — only when the repo owns the database)

Migrations are **managed and generated by Atlas from the Drizzle schema diff** and stored in `migrations/` with an `atlas.sum` integrity file. The pipeline: `drizzle-kit export` emits the desired DDL → Atlas diffs it against the migrations directory → a new timestamped `.sql` migration is written.

After changing any `*.sql.ts` file:

1. **Preview** the diff (no files written) — check for the package script, typically:
   `bun run db:preview-new-migration`
   (≈ `bunx drizzle-kit export > /tmp/diff.sql && atlas schema diff --from file://migrations --to file:///tmp/diff.sql --env <env>`)
2. Review the generated SQL. Watch for destructive statements (DROP COLUMN, DROP TABLE) that Atlas infers from renames — a rename shows up as drop+add; if data must survive, the migration needs manual rework and user sign-off.
3. **Generate** the migration:
   `bun run db:generate-migration` (≈ `atlas migrate diff --env <env>`)
4. Give the migration a descriptive name if the tool prompts/allows (`<timestamp>_add_orders_table.sql`).

Hard rules:

- **Never hand-edit an already-applied migration** and never edit `atlas.sum` manually — regenerate instead.
- Never write a migration `.sql` by hand for schema changes expressible in Drizzle; change the `*.sql.ts` and let Atlas diff it.
- Environments (`local`, remote, …) are defined in `atlas.hcl`, reading connection URLs from `.env`. Generating a migration only needs the dev-scratch database; applying to a real environment is a deliberate, user-approved step.

## Checklist

1. `*.sql.ts` created/edited under `tables/<domain>/`
2. `bun run tsc` passes (Drizzle defs are type-checked)
3. If the repo owns the DB: migration previewed, reviewed for destructive ops, generated. If not: definitions verified against the external database
4. DTOs updated **explicitly** if the API should expose the change (`dto-conventions` skill) — a new column is not automatically part of any DTO
